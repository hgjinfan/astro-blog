## 背景

Perch（我的个人主页项目）部署在一台甲骨文免费小鸡上：VM.Standard.E2.1.Micro，1 OCPU、1 GB 内存，首尔机房。发版流程很原始：SSH 上去 `git pull`，然后 `docker compose up -d --build`，在服务器本机构建。从开始构建到新容器起来，每次都要等 10 分钟以上，构建期间站点响应也被拖得很慢。

## 先入为主的猜测

第一反应是这台机器 CPU 太弱：1 核，构建慢理所当然。但我在开发环境顺手测了一下：`npm run build` 只要 0.35 秒，`npm test` 约 15 秒。esbuild 打包本身轻得不能再轻，1 核再弱，也不至于把几秒钟的活干成 10 分钟。那时间到底花在哪了？

## 拆构建日志

今晚发 v0.1.5 时，把构建日志按步骤拆开看耗时（BuildKit 每一步都有 DONE 时间）：

| 步骤 | 耗时 |
| --- | --- |
| 构建阶段 `npm ci`（完整依赖） | 469s |
| 运行阶段 `npm ci --omit=dev` | 419s |
| 导出镜像 | 98s |
| `npm run build` | 31.5s |
| 基础镜像拉取 | 0.1s（本地有缓存） |
| 其余 COPY 等步骤 | 合计不到 40s |

总墙钟约 12 分钟。两遍 `npm ci` 是并行跑的，互相抢这 1 核 1G——构建期间 load 冲到 24，可用内存只剩 283 MB——光这两步的墙钟就占了约 7.8 分钟。而 `npm run build` 的 31.5 秒还是被高负载拖出来的水分，正常应该是亚秒级。也就是说，真正花在「构建」上的时间只有几十秒，其余全在装依赖。

## 根因

**一、冷构建要装两遍依赖。** Dockerfile 是多阶段构建：构建阶段安装完整依赖做打包，运行阶段再安装一遍生产依赖。两次都是冷安装，全量走网络下载、解压、落盘。

**二、依赖层缓存结构性失效。** Dockerfile 已经把 `package*.json` 放在源码复制之前，依赖不变时 `npm ci` 这一层理论上可以走缓存。但每次发版都会改 `package.json` 里的 `version` 字段，`COPY package*.json` 的层哈希跟着变，`npm ci` 层每轮必然失效——依赖一个没动，也得全量重装。缓存不是没配，是被版本号顶掉了。

**三、小机器放大了一切。** 两个 `npm ci` 在 1 核 1G 上并行，不只是各自慢，还互相拖累；连导出镜像这种纯 IO 步骤，也被当时的高负载拖到了 98 秒。

## 优化方向

按收益排序：

1. **不在 VPS 上构建。** 在 CI 或开发机构建好镜像、推到镜像仓库，VPS 只负责 `docker pull` 运行。编译和依赖安装彻底移出这台小机器，这是最适合 1 核 VPS 的解法。
2. **给 `npm ci` 加 BuildKit 缓存挂载**（`--mount=type=cache,target=/root/.npm`）。如果必须在 VPS 构建：缓存挂载不参与层哈希，`version` 改了也不会被顶掉，下载过的包可以直接复用。
3. **合并两遍安装。** 构建阶段装完、打包后执行 `npm prune --omit=dev`，运行阶段直接复制裁剪后的 `node_modules`，省掉一遍冷安装；需要验证最终镜像里只含生产依赖。

## 小结

「服务器慢」是个太粗的结论。这次 12 分钟里，编译只占几十秒，剩下的都在重复下载、安装同一批依赖。先拆日志再下判断：`docker compose build --progress=plain` 会把每一步的耗时打出来，比猜 CPU 强弱靠谱得多。
